# Assumptions register

Every number, distribution, threshold or encoder choice the tooling or brief implies is listed here and labelled. Data is synthetic; nothing about the client is known beyond SPEC.md.

- A1: All data in this project is synthetic. No real borrower, firm, phone number or amount exists anywhere, including seed output.
- A2: Nothing is known about Company A beyond the brief (SPEC.md §1). No facts about the client or the regulator are invented; unclear items land here instead.
- A3: Ratlam has no branch row. Its one officer belongs to the Ujjain branch, Ratlam loans carry `branch_id = Ujjain`, and `territory` rows carry Ratlam pincodes (approved 2026-11-04).
- A4: Contact rule-set selection is by attempt date: `attempt_date_ist < 2027-01-01` -> `RBC2025_para100`, else `RECOVERY2026_100Y`. Both enforce 08:00-19:00 IST (approved 2026-11-04).
- A5: Seed targets about 22% roll behaviour for the opening cohort to match the scorecard baseline `logit(0.22)`; the dashboard target remains 16% (approved 2026-11-04).
- A6: Assignment utilisation = sum of loan weights / capacity_points, with no separate amount cap; large loans already pull more weight (approved 2026-11-04).
- A7: vite-plugin-pwa pinned at 1.3.0, not 2.0.0. 1.3.0 declares peer support for vite ^8; 2.0.0 is untested here and stays unused until a spike proves it (per standing instruction).
- A8: TypeScript pinned at 5.9.3 (not 7.0.2): typescript-eslint 8.72.1 declares peer support only up to <6.1.0, so 7.x would break the lint stack.
- A9: The gitleaks pre-commit hook requires the gitleaks binary on the contributor's machine (installed via brew here); CI carries the gitleaks job so history is still scanned if a local binary is missing.
- A10: The daily CSV contract is assumed to be "full list of every loan with DPD >= 1 as of the date" (SPEC.md §11 default); to be confirmed against the real sample file before it matters.
- A11: Paise stored as Drizzle `bigint` with `mode: 'number'` (not JS bigint) — Rs 25 lakh = 2.5e9 paise overflows int32, and `mode: 'number'` keeps JSON serialisation plain; domain values stay far below 2^53.
- A12: Enum value lists (roles, outcomes, GPS status, time confidence, compliance, promise status, message/batch statuses, payment sources) are defined once in src/shared/types.ts and shared by Drizzle pgEnum and validation code; exact labels are my choice where SPEC did not enumerate them (e.g. compliance: COMPLIANT / VIOLATION_DETECTED / FLAGGED).
- A13: contact_event NOT NULL floor: id, loan_id, kind, attempted_at_device, device_tz_offset_minutes, attempted_at_ist, within_window, rule_set; the rest nullable so partial device syncs can land before server enrichment.
- A14: message_outbox uniqueness on (promise_id, kind) intentionally exempts rows with promise_id NULL (T2/T6/T7 reminder kinds have no promise); the append-only trigger is statement-level and raises on any UPDATE/DELETE against contact_event.
- A15: score_log immutability is enforced in the write layer on Day 1 (unique (loan_id, as_of) only); a hard DB trigger for score_log is a deferred TDD item, contact_event immutability IS trigger-enforced.
- A16: Migrations run locally via pnpm db:migrate with DATABASE_URL from the local .env; the Vercel build never runs migrations (buildCommand is pnpm build only).
- A17: Demo reset plan (not built yet; built when the manager UI lands): "reset demo" is DEMO_MODE-only and manager-only. It runs inside one transaction: write the audit_log row (actor, action 'demo_reset', counts in detail), then `TRUNCATE contact_event, promise CASCADE` — message_outbox rows are removed by the same CASCADE since they reference promise. TRUNCATE deliberately bypasses the append-only UPDATE/DELETE trigger (triggers fire only for UPDATE/DELETE, not TRUNCATE), which is why the trigger can stay as-is. Loans, payments, snapshots, audit rows survive; contact_event/promise ids are client- or db-generated UUIDs so there is no sequence to reset.
- A18: The brief's sample extract (Loan ID, Borrower, Outstanding, DPD, Promise Date, Officer) has no Pin Code or Branch, but auto-assignment by pincode needs both; we assume the real daily export includes them and our sample CSV (data/sample_overdue.csv) adds Pin Code and Branch columns. The Officer column is the lender's own assignment: it is stored for reference but ignored by our auto-assignment rules.
- A19: Any active branch_manager can upload the whole company's daily import file, covering every branch, because the daily extract is a single company-wide export and splitting it per branch would be manual busywork; import writes and the errors download are manager-only, while officer-facing lists and dashboards stay branch-scoped as elsewhere in the spec (approved 2026-11-04).
- A20: `late_discovery` tags a loan absent from the previous snapshot with DPD > 30, but ONLY when a previous snapshot exists (previousCount > 0). On a first-ever import (no previous snapshot), no loan can be "late" because there is no baseline to compare against. A loan first seen at 35 DPD after a prior import is flagged; the same loan on a first-ever import is not (approved 2026-11-04).
- A21: The "primary officer" for the -0.10 assignment bonus is the territory-resolved officer for the loan: locality row beats pincode row, then the 452xxx prefix tiers, best `rank` wins inside a tier (ties broken by officer id). Only that one officer gets the bonus (approved 2026-11-05).
- A22: "Broken promise in the last 14 days" means a promise row with status `broken`/`broken_part` whose `promised_date` is within the last 14 calendar days of the assignment run date (promised_date anchored, deadline/resolved_at NOT yet observable because the promise tracker is deferred; approved 2026-11-05).
- A23: The assignment run's working day is Mon-Sat; Sunday never counts. Leave lengths are measured in working days (approved 2026-11-05).
- A24: An officer on 3+ consecutive working days of leave is excluded from the candidate pool for everyone: their existing loans reassign to the leave cover (or score), and a NEW loan whose territory-resolved officers are all on such leave goes to the queue (queued as `queue_unmapped` for the branch manager) (approved 2026-11-05).
- A25: `home_officer_id` is assignment-owned. The CSV Officer column stays bookkeeping-only (A18): it seeds `home_officer_id` on first insert and stays on queue/data-fix loans for reference, but any new loan assignment or score-based reassignment overwrites `home_officer_id` with the assigned officer; only a leave cover keeps the previous home. `apply_import` must not overwrite `home_officer_id` on continuing imports (assignment wrote it), or a working loan pointing at a bookkeeping officer could spuriously "revert" when that bookkeeping officer takes leave (approved 2026-11-05).
- A26: Assignment runs after every imported/replaced batch in its own transaction under a company-wide advisory lock (`assignment:run`); noop replays and aborted imports never run it. Outcomes are counted by reason into `import_batch.row_counts_json` so the import report carries them and a noop replay reproduces them verbatim (approved 2026-11-05).
- A27: `assignment_log` rows record officer changes only (`from_officer <> to_officer`). A status-only flip — e.g. a replaced import re-asserting a continuing loan as overdue and the runner re-queuing it — is a loan write without a log row, which is what makes a rerun of the whole batch produce zero assignment_log rows (approved 2026-11-05).
- A28: The import's loan upsert keeps re-asserting `status = 'overdue'` and the rest of the file's data on continuing loans, while leaving `home_officer_id` alone (A25). That lets a healed file row (usable phone appeared, unmapped pincode fixed) re-enter the worklist on the next assignment run; if the disqualifier persists, the runner re-queues it and no officer changed, so no new log row (approved 2026-11-05).
- A29: A `BLOCKED` attempt is not a contact. SPEC §7 defines blocked attempts as events blocked by rule enforcement (A4's window rules), so the officer never reached the borrower; only `CALL`/`VISIT`/`MESSAGE` make a loan "touched" for the return-of-leave revert rule (§10.6 "untouched loans without an open promise revert; touched ones stay"). The runner does not filter at load time; the planner compares the kind. `attemptedAt` boundaries are inclusive on both ends (approved 2026-11-05).
- A30 (auth numbers): the session cookie is `fc_session` (HttpOnly, Secure, SameSite=Lax, `Path=/`, Max-Age 7 days) carrying a 32-byte random base64url token of which only the sha256 is stored (`session.token_hash`); sessions expire 7 days after creation and the expiry is checked server-side at every lookup. Login rate limit: 5 failed attempts per 15-minute window keyed by username + client IP (first `X-Forwarded-For` entry, else `unknown`); the counter lives in the `login_attempt` table (`key`, `fail_count`, `window_start`) — amended the same day after a serverless review that rejected the original in-memory per-instance Map: it would reset with every invocation and is not shared across instances, so it enforced nothing on Vercel. The window opens at `window_start`; a row older than 15 minutes rolls into a fresh window on the next failure (no sweeper needed); 429 answers with `Retry-After`; a successful login deletes the row. Every failure mode answers the same generic `wrong username or PIN` (approved 2026-11-05; amended 2026-11-05: counter moved to the DB, migration 0003; Basic header path retired in the same review — cookie sessions are the only accepted API auth, and import-check logs in through the login endpoint).
- A31 (demo accounts): usernames `demo-manager` (branch_manager), `demo-officer-1`, `demo-officer-2` (field_officer), all `is_demo=true`, with the documented demo PIN `1234` hashed by the same scrypt as real users and a per-user salt. The PIN is a documented demo credential (docs/deployment.md), created by the demo seed config — never a real secret. - A32 (phone masking): no server response carries a full phone number. `maskPhone` considers digits only (importer-tolerated separators/`+91` prefixes get stripped), keeps the first two and the last two digits and fills the middle with X preserving length; under five meaningful digits yields null (nothing safely maskable). The loan detail and worklist payloads expose `mobileMasked`/`altMobileMasked` and never the raw `mobile`/`alt_mobile` columns — masking happens inside the data-access layer, so the shape cannot leak. The reveal flow arrives with the contact-window work (approved 2026-11-05).
- A33 (loan visibility): `GET /api/me/assignments` is officer-scoped — a field officer sees exactly their assigned loans with status `overdue`, ordered DPD descending then loan ascending; a manager gets 403 (`assignments are officer-scoped`). `GET /api/loans/:id` is visible to a field officer iff the loan's `assigned_officer_id` is theirs, and to a branch manager iff the loan's branch is theirs; every invisible or missing loan answers the same generic 404 so existence cannot be enumerated. Both routes take their actor from the cookie session only. The route data-access guard is a test (`routeDbGuard.test.ts` scanning api/ and src/server/app.ts for driver imports), and `/api/health` delegates its probe into the DAL; the DAL rule lives there (approved 2026-11-05).
- A34 (seed config file): every seed rate, count and distribution lives in `data/seed_config.yaml`, written in a strict YAML subset — `#` comments, one level of `section:` nesting, `key: value` scalars, comma-separated inline lists — parsed by a ~70-line purpose-built parser (scripts/seed/config.ts) that fails before any database write. - A51 (promise window numbers): SPEC 12's creation windows are IST calendar days anchored on the EVENT'S OWN attempted_at — the skew-corrected best estimate of when the attempt actually happened (amended 2026-11-06, prompt 10b: the original "server's IST today key" would wrongly judge a promise made offline on Monday against Thursday's clock). - A52 (time confidence): the device stamp grades three ways — attempted_at_device further than 2 min into the future beyond serverNow → `suspect` (a backwards clock jump, flagged but recorded, never silently dropped); |skew_estimate_ms| < 5 min → `high`; otherwise (unknown or large skew) → `low`. SPEC 7's high-confidence condition reads "skew < 5 min and last sync < 30 min ago"; there is no freshness field on the wire, so freshness is INFERRED from the skew magnitude: the client measures skew right after each sync response, so a small |skew| implies the stamp was taken while fresh. The 5-min threshold matches both SPEC conditions anyway. attempted_at_ist = device stamp − skew (best estimate of truth, falls back to the raw stamp when skew is unknown); within_window = device-stamp-in-window AND skew-corrected-in-window; compliance_status = VIOLATION_DETECTED when either derivation says outside — recorded on the event row (contact_event.compliance_status), never thrown away and never rejected (SPEC 7 layer b).
- A53 (assignment history probe): SPEC 6's "assignment changed" acceptance is answered in two probes: the loan is currently assigned to this officer, or not — and not is fine iff the officer appears in assignment_log for that loan as either hand (from_officer or to_officer). Either case accepts the event with assignmentChanged=true on the item result; an officer with no history link is rejected `loan_not_assigned_to_officer`. The OR covers both ends of the hand-over without a second query.
- A54 (idempotency + retry signature): a sync retry repeats the same event id with the same payload; the signature is [loan_id, kind, outcome, attempted_at_device epoch-ms, device_tz_offset_min] — skew_estimate_ms deliberately excluded because it can change between flushes of the same attempt. Same id + same payload answers `duplicate` (no second write, no second promise); same id + different payload keeps the FIRST write, logs an `event_duplicate_mismatch` audit row and still answers `duplicate` with reason payload_mismatch_kept_first; a lost DB race surfaces as `duplicate`/concurrent_duplicate from the insert's ON CONFLICT (id) DO NOTHING + returning. The batch envelope is 1..MAX_EVENT_BATCH(=20) items; every item is graded alone so one bad event never fails the flush (HTTP 200 while authenticated), and each response carries serverNow for the client's next skew estimate. synced_at can never ride the payload: the strict wire schema rejects any server-owned field outright (SERVER_EXCLUDED_FIELDS) and the insert sets syncedAt from the server clock.
- A55 (reschedule semantics): "one open promise per loan, max two reschedules per bucket stay" reads as: creating a promise while another is open is legal and IS the reschedule — inside the same transaction the old promise is marked superseded (resolved_at = sync instant, superseded_by = the new promise id), so the invariant "at most one open" always holds. rescheduleCount approximates "per bucket stay" as the number of the loan's promises currently in status superseded (read up to 100); at >= 2 the creation is rejected `reschedule_limit_reached` — a third re-timing needs a manager path no client offers yet.
- A56 (reveal limiter): the 30-reveals-per-officer-per-hour cap reuses the login_attempt table — one counter table, one fixed-window algorithm (windowDecision/incrementFixedWindow in rateLimit.ts) — under a namespaced key `reveal|<officerId>`, so the limit survives restarts and holds across serverless instances with zero new schema. Ordering is count-before-answer: the increment runs before the response, so a crash can lose a count but never overshoot (the safe direction — a lost increment weakens the limiter by at most one). The 429 carries Retry-After in seconds, same contract as the login throttle.
- A57 (amended 2026-11-06, prompt 10b — failed promises never reject the event + reveal cache scope): a promise_to_pay event whose business rules fail (A51/A55 reasons) now stores the CONTACT EVENT and skips only the promise row — the item answers `created` with `warnings: [{code: "promise_not_created", reason: <first validation reason>}]`. The original whole-item rejection (no event row at all) threw away the compliance record along with the bad side effect; the call/visit happened either way, SPEC 6 grades items one at a time precisely so nothing else is lost, and the warning keeps the officer's outbox visible about the missed promise instead of silently dropping it (the client shows the warning on the item). Still rejected WHOLE, with no warnings key: schema-invalid payloads (`invalid_event`), unknown loans, stranger loans (`loan_not_assigned_to_officer`) — there is nothing truthful to store for those — and a failed transaction write (`write_failed`). Separately, on the reveal endpoint: a revealed unmasked number may be cached by the client until the end of the IST day — the endpoint answers raw mobile/alt_mobile on success, every reveal is audited (A32 stands: every other response keeps masks), and revocability is not a goal; the rate limit is the only brake on repeated exposure.
- A58 (skew sign convention, amended 2026-11-06, prompt 10b): SPEC 7 words the estimate as skew = serverNow − (t_sent + t_received)/2, but the SERVER grades stamps as attempted_at_ist = device − skew (A52). For both to be true simultaneously the stored skew_estimate_ms must be the DEVICE ERROR (positive = device clock FAST), so the client stores the negation of SPEC 7's literal formula: estimateSkew = (t_sent + t_received)/2 − serverNowMs. Fast device → positive skew → server subtracts → lands on true time; the client's own window gate runs the same correctedNowMs = device − skew. Tested both ways in src/client/sync/engine.test.ts (sign convention + storage from a batch response).
- A59 (client offline-sync mechanics, 2026-11-06, prompt 10b): (1) Undo is real: a fresh outcome is queued with not_before = now + 5 s, so Undo (allowed only before not_before) deletes it locally before any flush can carry it out — after the hold the item may already be on the server and Undo is refused. (2) Backoff per failed flush attempt: 2 s doubling as base × 2^attempt with jitter uniform in [half, full] of the step, 5 min cap, multiplier reset on online/foreground and on any success; 429/5xx/timeouts/network errors set not_before and stay pending; other 4xx mark items failed with visible Retry/Discard and are never auto-retried. (3) Sync triggers: app start, online, visibilitychange-to-visible, after each save (a kick 5.25 s later, honouring the undo hold), every 45 s while visible with pending items, and manual Sync now; navigator.onLine is deliberately ignored (flush attempts offline are normal and just back off). (4) Synced items stay in the outbox for 24 h so the Sync screen can show them, then are swept at the next flush. (5) BLOCKED attempts (window enforcement) carry the rule code `CONTACT_WINDOW_CLOSED` in the event note — the rule-SET version is stamped server-side from the attempt date on sync, and no borrower text is ever stored. (6) The revealed unmasked number is cached client-side until the end of the IST day (A57 scope), keyed by loan. (7) navigator.storage.persist() is requested after the first save and the answer is remembered; the Sync screen warns while items are pending and the grant was refused. (8) fake-indexeddb is the SPEC 3-named test double for IndexedDB — no runtime dependency. (9) Layout audit found and fixed three sub-48px tap targets (sync pill, Sync now, Undo) and hardened both Playwright scripts against orphan dev servers.
