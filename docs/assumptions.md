# Assumptions register

Every number, distribution, threshold or encoder choice the tooling or brief implies is listed here and labelled. Data is synthetic; nothing about the client is known beyond SPEC.md.

- A1: All data in this project is synthetic. No real borrower, firm, phone number or amount exists anywhere, including seed output.
- A2: Nothing is known about Company A beyond the brief (SPEC.md §1). No facts about the client or the regulator are invented; unclear items land here instead.
- A3: Ratlam has no branch row. Its one officer belongs to the Ujjain branch, Ratlam loans carry `branch_id = Ujjain`, and `territory` rows carry Ratlam pincodes (approved 2026-11-04).
- A4: Contact rule-set selection is by attempt date: `attempt_date_ist < 2027-01-01` -> `RBC2025_para100`, else `RECOVERY2026_100Y`. Both enforce 08:00-19:00 IST (approved 2026-11-04).
- A5: Seed targets about 22% roll behaviour for the opening cohort to match the scorecard baseline `logit(0.22)`; the dashboard target remains 16% (approved 2026-11-04).
- A6: Assignment utilisation = sum of loan weights / capacity_points, with no separate amount cap; large loans already pull more weight (approved 2026-11-04).
- A7: vite-plugin-pwa pinned at 1.3.0, not 2.0.0. 1.3.0 declares peer support for vite ^8; 2.0.0 is untested here and stays unused until a spike proves it (per standing instruction).
- A8: TypeScript pinned at 5.9.3 (not 7.0.2): typescript-eslint 8.72.1 declares peer support only up to <6.1.0, so 7.x would break the lint stack.
- A9: The gitleaks pre-commit hook requires the gitleaks binary on the contributor's machine (installed via brew here); CI carries the gitleaks job so history is still scanned if a local binary is missing.
- A10: The daily CSV contract is assumed to be "full list of every loan with DPD >= 1 as of the date" (SPEC.md §11 default); to be confirmed against the real sample file before it matters.
- A11: Paise stored as Drizzle `bigint` with `mode: 'number'` (not JS bigint) — Rs 25 lakh = 2.5e9 paise overflows int32, and `mode: 'number'` keeps JSON serialisation plain; domain values stay far below 2^53.
- A12: Enum value lists (roles, outcomes, GPS status, time confidence, compliance, promise status, message/batch statuses, payment sources) are defined once in src/shared/types.ts and shared by Drizzle pgEnum and validation code; exact labels are my choice where SPEC did not enumerate them (e.g. compliance: COMPLIANT / VIOLATION_DETECTED / FLAGGED).
- A13: contact_event NOT NULL floor: id, loan_id, kind, attempted_at_device, device_tz_offset_minutes, attempted_at_ist, within_window, rule_set; the rest nullable so partial device syncs can land before server enrichment.
- A14: message_outbox uniqueness on (promise_id, kind) intentionally exempts rows with promise_id NULL (T2/T6/T7 reminder kinds have no promise); the append-only trigger is statement-level and raises on any UPDATE/DELETE against contact_event.
- A15: score_log immutability is enforced in the write layer on Day 1 (unique (loan_id, as_of) only); a hard DB trigger for score_log is a deferred TDD item, contact_event immutability IS trigger-enforced.
- A16: Migrations run locally via pnpm db:migrate with DATABASE_URL from the local .env; the Vercel build never runs migrations (buildCommand is pnpm build only).
- A17: Demo reset plan (not built yet; built when the manager UI lands): "reset demo" is DEMO_MODE-only and manager-only. It runs inside one transaction: write the audit_log row (actor, action 'demo_reset', counts in detail), then `TRUNCATE contact_event, promise CASCADE` — message_outbox rows are removed by the same CASCADE since they reference promise. TRUNCATE deliberately bypasses the append-only UPDATE/DELETE trigger (triggers fire only for UPDATE/DELETE, not TRUNCATE), which is why the trigger can stay as-is. Loans, payments, snapshots, audit rows survive; contact_event/promise ids are client- or db-generated UUIDs so there is no sequence to reset.
- A18: The brief's sample extract (Loan ID, Borrower, Outstanding, DPD, Promise Date, Officer) has no Pin Code or Branch, but auto-assignment by pincode needs both; we assume the real daily export includes them and our sample CSV (data/sample_overdue.csv) adds Pin Code and Branch columns. The Officer column is the lender's own assignment: it is stored for reference but ignored by our auto-assignment rules.
- A19: Any active branch_manager can upload the whole company's daily import file, covering every branch, because the daily extract is a single company-wide export and splitting it per branch would be manual busywork; import writes and the errors download are manager-only, while officer-facing lists and dashboards stay branch-scoped as elsewhere in the spec (approved 2026-11-04).
- A20: `late_discovery` tags a loan absent from the previous snapshot with DPD > 30, but ONLY when a previous snapshot exists (previousCount > 0). On a first-ever import (no previous snapshot), no loan can be "late" because there is no baseline to compare against. A loan first seen at 35 DPD after a prior import is flagged; the same loan on a first-ever import is not (approved 2026-11-04).
